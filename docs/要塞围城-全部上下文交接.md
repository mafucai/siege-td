## 二、渲染链（反汇编确认）

### 2.1 初始化链

```
nativeInit
  → ecGameInit(480, 320, 0, 屏幕W, 屏幕H)
    → ecGraphics::Init(480, 320, 320, 0, 屏幕W, 屏幕H)
       - glViewport(0, 0, 屏幕W, 屏幕H)      ← 物理屏幕
       - glOrthof(0, 480, 0, 320, ...)      ← 逻辑坐标
```

`nativeResize` **只打日志，不做任何事**。

### 2.2 **核心矛盾（一切的根源）**

```asm
; ecImage::Init @0x7363e
7364e: ldr  r0, [r1, #4]     ; texture->w
73654: str  r0, [r4, #28]    ; +0x1C = 纹理宽（UV 分母）
73656: ldr  r0, [r5, #8]     ; texture->h
7365c: str  r0, [r4, #32]    ; +0x20 = 纹理高

73668: ldr  r3, [sp, #40]    ; r3 = w（参数）
7366e: str  r3, [r4, #12]    ; +0x0C = 显示宽   ← 同一个 w
73670: ldr  r3, [sp, #44]    ; r3 = h
73676: str  r3, [r4, #16]    ; +0x10 = 显示高   ← 同一个 h

; UV 计算（用栈上原始 w/h）
7368e: ldr  r1, [sp, #40]    ; w
73692: r0 = texX
73694: addsf3               ; texX + w
7369a: fdiv                 ; u2 = (texX+w) / 纹理宽
```

**关键结论**：
- `+0x0C/+0x10` 管**显示尺寸**
- `[sp,#40]/[sp,#44]`（栈上参数副本）管 **UV 计算**
- **两者来源不同！** 这是唯一可以分离的突破口。

### 2.3 `ecImage` 字段布局（反汇编确认）

| 偏移 | 含义 | 写入者 | 读者 |
|---|---|---|---|
| `+0x00` | texture 指针 | Init | Render* |
| `+0x04` | texX | Init/SetTextureRect | Render* |
| `+0x08` | texY | Init/SetTextureRect | Render* |
| `+0x0C` | **显示宽 w** | Init/SetTextureRect | Render/RenderEx |
| `+0x10` | **显示高 h** | Init/SetTextureRect | Render/RenderEx |
| `+0x14` | anchorX（=refx） | Init | RenderEx |
| `+0x18` | anchorY（=refy） | Init | RenderEx |
| `+0x1C` | **纹理宽**（UV 分母） | Init | Init |
| `+0x20` | 纹理高 | Init | Init |
| `+0x24/+0x28/+0x38/+0x3C/+0x4C` | **渲染时临时顶点**（不是持久字段） | Render* 每次重算 | — |
| `+0x30/+0x34` | UV 坐标 u1,u2 | Init/SetTextureRect | — |
| `+0x44/+0x48` | v1,v2 | Init/SetTextureRect | — |

**⚠️ 别被 `+0x24` 之类骗了**：反汇编显示它们只是渲染过程中临时存顶点，下次渲染会重算。不是可用的尺寸字段。

### 2.4 渲染路径

| 方法 | 地址 | 用途 | 尺寸来源 |
|---|---|---|---|
| `ecImage::Render(x,y)` | `0x73774` | UI 图 | `+0x0C/+0x10` × `g_contenscalefactor` |
| `ecImage::Render(x,y,w,h)` | `0x73838` | 指定尺寸 | 外部参数 |
| `ecImage::RenderEx(x,y,w,h,scale)` | `0x738fc` | 场景元素 | `+0x0C/+0x10` × scale |
| `ecImage::RenderEx(7参数)` | `0x73af4` | 复杂场景 | 同上 |
| `ecImage::RenderStretch` | `0x73dc0` | 拉伸 | `+0x0C` |
| `ecImage::Render4V` | `0x73e48` | 四边形顶点 | 外部顶点 |

### 2.5 其他关键地址

| 函数 | 地址 | 大小 |
|---|---|---|
| `ecImage::Init` | `0x7363e` | 174 |
| `ecImage::SetTextureRect` | `0x7450e` | 136 |

## 三、图片高清化（已做成的部分）

### 3.1 结论：原版模糊的物理原因

```
原图 64×128 的长矛兵
逻辑空间 480 宽，单位占 64 = 13.3%
1080p 屏（2400 宽）上显示 = 320 像素
64 → 320，拉伸 5 倍
```

**素材分辨率不够，任何引擎放大都会糊。**

### 3.2 三种高清化方案实测结果

| 方案 | 效果 | 代价 | 结论 |
|---|---|---|---|
| **代码放大（xBR）** | 边缘锐利不糊，但**细节没增加** | 0 元 / 110 秒 | ✅ 已实现 |
| **AI 重画** | **真的增加细节**（砖纹、窗框、木梁） | 约 2 美元 / 28 分钟 | ✅ 已做 20 张 |
| 程序化矢量重绘 | 风格会变 | - | ❌ 没做 |

**视觉模型实测评价**：
- xBR 版：「边缘清晰，但块感明显，细节丢失严重」
- AI 版：「细节丰富一个数量级，但不是同一个城堡（结构差异大）」

**⇒ 无法同时满足「图片不变」和「变清晰」，这是物理限制。**

## 四、引擎 patch（核心，也是失败的地方）

### 4.1 代码洞

```
0xd2270 ~ 0xd246f（512 字节全零）
位置：.rodata 段
段属性：SHF_ALLOC 但**没有 SHF_EXECINSTR**
所在 PT_LOAD：flags=0x5（PF_X | PF_R）← 可执行
无任何指针引用
```

**实测可执行**（T0 空 patch 能正常启动）。

### 4.2 所有尝试过的 patch 方案

| 版本 | 改哪里 | 结果 |
|---|---|---|
| A | `nativeInit` 480×320 → 960×640 | ❌ 画面缩到左上角 1/4 |
| C/M1/M2 | 整图放大 1.69 倍 | ⚠️ 开屏高清，游戏内仍糊 |
| N1/N2 | 同尺寸锐化 | ❌ 无效（超采样 3.375× 杀死细节） |
| P1 | `GetAbsRect×2` + `g_contenscalefactor=0.5` | ❌ 闪退 |
| Q1 | 修代码洞起点 + cbz 编码 | ❌ 闪退 |
| R1/v4 | `ecImage::Init` 的 texW/texH ÷2 | ❌ 分屏（字体也被÷2） |
| S1/v5 | 改 `ecImage::C1(tex,TextureRect)` | ❌ 闪退 / 四屏 |
| U1/v6 | 修 r1 未初始化 | ❌ 四屏 |
| F1 | UV 与显示分离（回跳 73678） | ❌ 四屏 |
| **N0** | 空 patch（回跳 73678） | ❌ **黑屏** |
| **N1** | 空 patch（回跳 73676） | ✅ **能开，画面正常** |
| **LAST** | w/h ÷2（回跳 73678） | ⚠️ 结果未知 |
| **LAST2** | w/h ÷2 + ui 图集放大 | ⚠️ 结果未知 |

### 4.3 **关键发现：黑屏根因**

```asm
73674: str  r7, [r4, #8]     ; texY
73676: str  r3, [r4, #16]    ; +0x10 = 显示高 h  ← 这条不能跳过
73678: adds r0, r6, #0       ; UV 计算起点
```

**N0 回跳 `0x73678`，跳过了 `73676`，导致 `+0x10` 永远是 0 → 所有图高度 0 → 黑屏。**

**N1 改为回跳 `0x73676` 后正常。**

### 4.4 最后一个 patch 的完整代码

```asm
; A) 跳转点：0x73668 覆盖 14 字节
0x73668: b.w  0xd2270
0x7366c: nop ×5

; B) 洞代码 @0xd2270（36 字节）
0xd2270: ldr  r3, [sp, #0x28]   ; 9b0a  w
0xd2272: str  r5, [r4]          ; 6025  this->tex = texture
0xd2274: ldr  r5, [r4, #0x1c]   ; 69e5  纹理宽
0xd2276: ldr  r1, [pc, #0x18]   ; 4906  0x00800000
0xd2278: cbz  r3, +6            ; b103
0xd227a: subs r3, r3, r1        ; 1a5b  w/2（float 指数-1）
0xd227c: str  r3, [r4, #0xc]    ; 60e3  +0x0C = w/2
0xd227e: ldr  r3, [sp, #0x2c]   ; 9b0b  h
0xd2280: cbz  r3, +6            ; b103
0xd2282: subs r3, r3, r1        ; 1a5b  h/2
0xd2284: str  r3, [r4, #0x10]   ; 6123  +0x10 = h/2
0xd2286: str  r6, [r4, #4]      ; 6066  texX
0xd2288: str  r7, [r4, #8]      ; 60a7  texY
0xd228a: b.w  0x73678           ; 回 UV 计算
0xd228e: nop
0xd2290: .word 0x00800000       ; 常量池
```

**数学原理**：
```
图片 ×2 → 纹理宽 realW×2
xml 的 x/y/w/h ×2，refx/refy 不变
显示尺寸 = (2w)/2 = w        ✓ 与原版一致
UV = (2texX)/(2realW) = texX/realW  ✓ 与原版一致
```

### 4.5 `b.w` 编码（踩过坑）

```python
def b_w(from_va, to_va):
    off = to_va - (from_va + 4)
    imm = off & 0x01FFFFFF
    S=(imm>>24)&1; I1=(imm>>23)&1; I2=(imm>>22)&1
    imm10=(imm>>12)&0x3FF; imm11=(imm>>1)&0x7FF
    J1=(I1^S)^1; J2=(I2^S)^1        # ← 必须 XOR S，否则地址错
    hw1 = 0xF000|(S<<10)|imm10
    hw2 = 0x9000|(J1<<13)|(J2<<11)|imm11
```

**验证方法**：用 `arm-linux-gnueabihf-gcc` 生成标准答案逐字节比对。

### 4.6 资源必须用 `build_w`

```
build_v/assets   refx/refy 也 ×2   ← 错的！会四屏/闪退
build_w/assets   refx/refy 不变     ← 正确
```

原因：patch 没有处理 `refx/refy`，它们必须保持原值。

**Ghidra 地址 = 实际地址 + 0x10000**（image base）。

## 六、**已经证伪的假设（不要再试）**

每一条都花过真实时间，请直接跳过：

| 假设 | 为什么错 |
|---|---|
| 改渲染分辨率（A 方案） | `ecGraphics::Init` 硬编码 `cmp r1,#320` 判断缩放档位，105 处调用依赖它 |
| 改 `g_contenscalefactor` | 全局缩放影响场景/粒子，UI 补偿不了 |
| `+0x24/+0x38/+0x3C/+0x4C` 是独立尺寸字段 | 反汇编确认只是渲染时临时顶点 |
| `RenderEx` 用另一套尺寸 | 它也读 `+0x0C`，只是算法不同 |
| `refy=8` 导致崩溃 | 只是 4 像素偏移，不会崩 |
| 改 `ecImage::Init` 就够（不影响字体） | 字体也走 `Init`，会被一起改 |
| 改 `ecImage::C1(tex,TextureRect)` 能避开字体 | 但这条路径只有 13 个调用者，改不到场景元素 |
| 代码洞必须放 `.text` | `.rodata` 在 PT_LOAD X 段，实测可执行 |
| `0xd226c` 是零区起点 | 那里有 int 值 4，从 `0xd2270` 开始才是零 |
| `cbz` 编码是 `0xB100｜(i<<3)｜rn` | 正确是 `i = off>>1`（off 从 PC+4 算） |
| Ghidra 的 `0x8363e` 是 `Init` | 加了 image base，真实是 `0x7363e` |
| 反编译能得到 C 代码 | 自编译的 arm64 decompile 会卡住，只有静态分析可用 |

## 九、给下一个 AI 的忠告

### 9.1 我做错的三件事

## 十、一句话总结

**引擎的限制是真实的**：`w/h` 同时管显示尺寸和 UV 分子，改一个必坏另一个。
